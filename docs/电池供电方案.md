# 电池供电方案（已否决）

> ⛔ **本文档已作废，仅作分析留档。**
>
> **实测确认板上稳压是 AMS1117，静态电流 ~5 mA** —— 比 ESP32-S3 深度睡眠
> （8.14 µA）大 600 倍。电池方案省下的电会被 LDO 完全吃掉，
> **方案 B/C 全部失效**，方案 A 也只剩 4~7 天。
>
> → **改用外供电，见 [外供电方案.md](外供电方案.md)**。
>
> 保留本文是因为里面的功耗拆解、官方实测数据、GPIO 占用仍然有参考价值；
> 且如果以后换掉 LDO，电池路线还能捡回来。

## 一、结论速览

| 方案 | 平均电流 | 2000mAh 续航 | 3000mAh 续航 | 数据延迟 | 固件改动 |
|---|---|---|---|---|---|
| **A 常在线**（推荐起点） | ~18 mA | **4.6 天** | **7 天** | 即时 | 只需改广播间隔 |
| **B 定时唤醒**（进阶） | ~4.1 mA | **20 天** | **30 天** | ≤10 分钟 | 需加深度睡眠 |
| **C 极省电**（不推荐） | ~0.34 mA | 200 天+ | 300 天 | ≤1 小时 | 需加深度睡眠 |

**为什么不能更省**：ESP32-S3 是 BLE 外设（GATT Server），**必须保持广播，主机才能找到它**。
一进深度睡眠，BLE 协议栈整个关掉，主机扫不到 → 天气就推不进来。
所以「续航」和「响应速度」是直接对立的，只能选一个点。

**推荐 A 起步**：改动最小（一行参数），4~7 天充一次，体验和插线几乎一样。
用一段时间觉得充电烦，再升级到 B。

## 三、功耗拆解

### 3.1 官方实测基准

Espressif 官方对 **ESP32-S3-WROOM-1** 的实测（[文档](https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-guides/current-consumption-measurement-modules.html)）：

| 模式 | 电流 | 功耗 |
|---|---|---|
| **Deep-sleep** | **8.14 µA** | 26.85 µW |
| **Active**（240MHz 全速） | **23.88 mA** | 78.32 mW |

> 这两个数字是本方案的地基 —— 说明「睡」和「醒」差了 **2900 倍**。

### 3.2 各部分电流

| 部件 | 状态 | 电流 | 数据来源 |
|---|---|---|---|
| ESP32-S3 | 深度睡眠（RTC 保持） | **8.14 µA** | ✅ 官方实测 |
| ESP32-S3 | BLE 广播，间隔 1000ms | ~10~15 mA | ⚠️ 估算 |
| ESP32-S3 | Active 全速 | 23.88 mA | ✅ 官方实测 |
| ESP32-S3 | BLE 连接瞬间（握手 + 写数据） | ~120 mA | ⚠️ 手册峰值 |
| EPD 屏 | **刷新中** | ~10~15 mA | ⚠️ 估算（手册 4.61mA 是均值） |
| EPD 屏 | **静态保持画面** | **0 mA** | ✅ 双稳态特性 |
| LDO | 静态电流 | 3~40 µA | 看型号 |
| LDO | 转换损耗 | ~15~20% | — |

> EPD 的「零功耗保持」是这个方案最大的优势——**屏幕亮着不费电，只有刷新费电**。
> 标 ⚠️ 的是估算值，标 ✅ 的是官方数据或物理特性。

### 3.3 一次刷新耗多少电

```
20 秒 × 12 mA = 0.067 mAh
```

一天刷 4 次 ≈ **0.27 mAh/天** —— 相对总耗电可以忽略。

**结论：耗电大头是 BLE 广播，不是屏幕。**

### 3.4 三种方案的计算

**A 常在线**

```
BLE 广播（1s 间隔，含 CPU）    12~15 mA
LDO 损耗（/0.85）              折算后 ≈ 15~18 mA
──────────────────────────────────────────
平均 15~18 mA
2000mAh ÷ 18mA = 111 小时 ≈ 4.6 天
3000mAh ÷ 18mA = 167 小时 ≈ 7.0 天
→ 保守说 「5~7 天」
```

> 若广播间隔保持默认（约 100~200ms），电流会接近 Active 的 23.88mA，
> 续航缩到 3~4 天。**拉长广播间隔是零成本的省电手段。**

**B 定时唤醒**（每 10 分钟醒一次，广播 120 秒）

```
每天活跃：144 次 × (2s 启动 + 120s 广播) = 17568s ≈ 4.9 小时
活跃耗电：4.9h × 20mA = 98 mAh
睡眠耗电：(24-4.9)h × 0.008mA ≈ 0.15 mAh
每天合计 ≈ 98 mAh
──────────────────────────────────────────
2000mAh ÷ 98 = 20 天
3000mAh ÷ 98 = 30 天
→ 保守说 「20~30 天」
```

**C 极省电**（每小时醒一次，广播 60 秒）

```
每天活跃：24 × 62s = 1488s ≈ 0.41 小时
每天耗电：0.41 × 20 = 8.2 mAh
2000mAh ÷ 8.2 ≈ 244 天
```

数据延迟最大 1 小时，对"看今天穿什么"意义不大，**不推荐**。

## 四、推荐方案 A（常在线）

### 4.0 最省事选项（想零折腾选这个）

不想碰板子的 3V3 脚，就买**「18650 移动电源模块」**——
电池盒 + 充电 + 5V 升压做在一块板上，淘宝 ¥10~15：

```
18650 电池 → [充电+升压一体板] → 5V 排针/USB → 板子 5V 脚
```

- ✅ **零风险**：完全不碰板子内部，走官方 5V 输入
- ✅ 免焊接、免调试
- ❌ 效率低（3.7V→5V→3.3V 两级，约 56%），续航打折：

| 供电方式 | 总效率 | 2000mAh 续航 |
|---|---|---|
| 直供 3.3V（§4.1） | ~85% | 4.6 天 |
| **一体板 5V**（本节） | ~56% | **3.5 天** |

> 差 25% 续航换零风险。**第一次做建议先用这个把东西跑起来**，
> 确认整套流程没问题，再考虑改成直供。

### 4.3 ⚠️ 关键：3V3 脚能不能直接灌电

**必须先确认**，否则可能烧板载 LDO。

板上的 `3V3` 如果只是 **LDO 输出脚**，外接电源灌进去会和板载 LDO 打架。
如果是 **电源输入脚**（板载 LDO 只给 USB 用），就没问题。

**验证方法**（万用表，断电状态）：

1. 红表笔点 `3V3` 脚，黑表笔点 `GND`
2. 用**二极管档**测，读数是 0.4~0.7V → 有 LDO 输出，**别直接灌**
3. 读数无穷大（OL）→ 可以直接接

**如果读数是 0.4~0.7V**（大概率），两种处理：
- 用 **5V 脚**输入（板载 LDO 正常工作）→ 需要把电池升压到 5V，效率损失大（~55%）
- **断开板载 LDO 输出**（通常是个 SOT-23 三脚 IC，吹掉或撬掉那颗脚）→ 再接 3V3

> 这一步不确定就别动手，先用 USB 供着。或者拍照发我，我帮你认 LDO 位置。

## 五、方案 B（定时唤醒）

### 5.1 额外改动

```
每 10 分钟：
  醒来（2s 初始化 BLE）
    ↓
  广播 need_sync=1，持续 120 秒
    ↓
  ┌── 主机连上并推送 → 刷新屏幕 → 睡
  └── 没人连 → 120 秒后自己睡
    ↓
  esp_deep_sleep_start()   (8.14 µA，官方实测)
```

**主机侧不用改**：服务的 3 秒探测 / 60 秒周期，正好能覆盖 120 秒的广播窗口。

### 5.2 固件改动点

| 位置 | 改动 |
|---|---|
| `setup()` | 判断 `esp_sleep_get_wakeup_cause()` |
| `loop()` | 广播窗口计时，超时进深度睡眠 |
| 唤醒源 | `esp_sleep_enable_timer_wakeup(10 * 60 * 1000000)` |
| 状态保持 | 刷新时间/最后数据存 RTC 内存或 NVS |

注意：**深度睡眠醒来 = 重启，`setup()` 会重跑**。
好消息是 `s_needSync` 会重置为 `true`，正好触发主机推送。

### 5.3 ⚠️ 前提：LDO 静态电流必须够小

方案 B 能不能成立，**卡在稳压器上**，不在固件。

ESP32-S3 深度睡眠只有 **8.14 µA**，但如果前面的 LDO 静态就吃 5 mA，
那睡多久都没意义 —— 睡眠收益被 LDO 完全抵消。

| LDO 型号 | 静态电流 | 对方案 B 的影响 |
|---|---|---|
| **AMS1117-3.3** | **~5 mA** ⚠️ | ❌ **直接毁掉方案 B**（比整机睡眠大 600 倍） |
| ME6211 | ~40 µA | ⚠️ 勉强，续航打 7 折 |
| RT9013 | ~25 µA | ✅ 可用 |
| **TPS7A02** | **~25 nA** | ✅✅ 最优 |
| TPS63020（DC-DC） | ~50 µA | ✅ 可用 |

**先确认板上那颗 LDO 是什么型号**：
- 丝印 `AMS1117` / `1117` → 如果是方案 B，**必须旁路或换掉**
- 方案 A（常在线）不受影响，5mA 相对 18mA 只占 3%

> AMS1117 是开发板上最常见的，静态 5mA 是它的著名缺点。
> 这也是很多「ESP32 深度睡眠只有几天」的隐藏原因。

### 5.4 代价

- 数据最多延迟 10 分钟
- 屏幕刷新前那一刻的画面是旧的
- 主机日志会周期性出现"设备不在广播"（正常，不是故障）

## 六、电池电量检测（可选）

### 6.1 分压电阻

```
电池 4.2V(满) ~ 3.0V(空)
        ↓
   ┌────┴────┐
   │  1MΩ    │
   └────┬────┘
        ├──────→ GPIO 4 (ADC1_CH3)
   ┌────┴────┐
   │  470K   │
   └────┬────┘
        │
       GND
```

- ADC 电压 = 电池 × 470/(1000+470) = 电池 × 0.32
- 4.2V → 1.34V（安全，ADC 上限 3.3V）
- 3.0V → 0.96V
- 分压静态电流 = 4.2 / 1.47MΩ ≈ **2.9 µA**（可忽略）

### 6.2 读数代码

```c
#define PIN_VBAT 4

float readBatteryVoltage() {
    // 12bit ADC，11dB 衰减：量程 0~3.1V 左右
    analogSetPinAttenuation(PIN_VBAT, ADC_11db);
    int raw = analogRead(PIN_VBAT);          // 0~4095
    float vadc = raw * 3.3f / 4095.0f;
    return vadc / 0.3197f;                    // 除以分压比
}
```

> 实际分压比按电阻实测值算，别用标称值。标称 1M+470K 误差 ±5%，
> **建议用万用表量实际电压反推**，否则显示会偏。

## 七、充电

### 7.1 TP4056 参数

| 项 | 值 |
|---|---|
| 充电电流 | 默认 1A（由 PROG 电阻决定） |
| 2600mAh 电池 | 建议 **0.5C = 1.3A**，1A 也可以（更保守） |

| 指示灯 | 红=充电中，蓝/绿=充满 |

**改充电电流**：TP4056 的 `PROG` 脚接电阻到地
`I = 1200 / R(kΩ)`，1A 用 1.2K，0.5A 用 2.4K。

### 7.2 注意

- TP4056 **没有过放保护**（只有过充），所以电池**必须自带保护板**
- 充电时设备可以同时工作（OUT 脚直接给负载）
- 充电时发热正常，别包在密闭壳里

## 九、哪些是实测、哪些是估算

| 项 | 数值 | 可信度 | 怎么验 |
|---|---|---|---|
| 深度睡眠 | 8.14 µA | ✅ **Espressif 官方实测** | 不用再测 |
| Active 全速 | 23.88 mA | ✅ **Espressif 官方实测** | 不用再测 |
| EPD 静态保持 | 0 mA | ✅ 双稳态物理特性 | 不用再测 |
| **BLE 广播平均电流** | 10~15 mA | ⚠️ **估算，最需要实测** | USB 功耗仪串在供电回路 |
| EPD 刷新电流 | 10~15 mA | ⚠️ 估算 | 同上，刷新时观察 |
| LDO 损耗 | 15~20% | ⚠️ 按型号 | 查 LDO 手册 |

量出当前固件的实时电流，再按上面公式算。比我估的准。

> 之所以 BLE 广播这一项没法定死：它同时取决于广播间隔、CPU 频率、
> 有没有开 power management，差异能有 2~3 倍。所以这一项**必须实测**。

## 附：NEED_SYNC 广播在省电方案中的作用

固件已经在广播包的 Manufacturer Data 里带了「需要同步」标志：

```
FF FF 01 XX     bit0=1 → 数据过期，请推送
```

这在省电方案里尤其有用：

- **方案 B** 每次醒来广播时标志为 1 → 主机一看到就立刻推，不用等定时
- 刷完屏标志清 0 → 主机不会重复推，避免多余连接
- 主机探测到 `need_sync=0` 就不连接 → **这一轮完全没无线功耗**

所以方案 B 的实际耗电可能比估算更低——因为大部分醒来轮次主机都会立刻推完就睡。
